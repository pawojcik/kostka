Spark settings this page models

      

        
SettingDefaultWhere you see it

        
          
spark.task.maxFailures4Task failure: the fourth failure of one task aborts the job.

          
spark.stage.maxConsecutiveAttempts4Executor lost: a stage may fail on FetchFailed this many times before the job is aborted.

          
spark.shuffle.service.enabledfalseExecutor lost: with it on, shuffle files outlive their executor.

          
spark.speculationfalseStraggler: turned on in that example.

          
spark.speculation.quantile0.75Straggler: copies start once 75% of a stage's tasks are done.

          
spark.speculation.multiplier1.5Straggler: a task is slow once it runs 1.5 × the median.

          
spark.sql.shuffle.partitions2004 here, so every reduce task fits on screen.

          
spark.sql.files.maxPartitionBytes128 MBOne scan task per split: 8 splits for store_sales, 2 for item.

        
      

    

    

      
What is simplified

      
    
        
  • Time moves in ticks, not seconds, and a task fetches all its shuffle input in its first tick.
    • 
        
  • The scheduler is FIFO: lower stage ids first, then the executor with the most free cores. Data locality, delay scheduling and AQE are left out.
    • 
        
  • Executors are not replaced after they are lost. With dynamic allocation, the cluster manager would usually start a new one.
    • 
        
  • Shuffle files live until the driver's ContextCleaner removes them, which can be long after the job ends; here they stay until the end.
    • 
      

    

  


  

    

      
Trino settings this page models

      

        
SettingDefaultWhere you see it

        
          
retry-policyNONEEvery example: NONE fails the query on any task failure, QUERY re-runs the whole query, TASK re-runs single tasks.

          
query-retry-attempts4retry-policy=QUERY: how many times the whole query may restart.

          
task-retry-attempts-per-task4retry-policy=TASK: how many times one task may be retried.

          
exchange-manager.namenoneretry-policy=TASK needs it (for example filesystem on S3 or HDFS) to spool exchange data.

          
query.execution-policyphasedstore_sales splits are held back until the item build side is done.

          
node-scheduler.max-pending-splits-per-task162 here: each task holds at most 2 unfinished splits, and is topped up as they finish.

          
task.max-worker-threads2 × cores2 per worker here, shared by every driver on the worker.

        
      

    

    

      
What is simplified

      
    
        
  • One tick is one scheduling quantum (about 1 s in Trino). Each thread runs the runnable driver that has used the least CPU, a stand-in for the multilevel feedback queue.
    • 
        
  • A stage-1 task folds in every page queued for it in one quantum.
    • 
        
  • With retry-policy=TASK, a stage starts only after the stage before it has finished. Real fault-tolerant execution can start some downstream work earlier.
    • 
        
  • Dynamic filtering, memory limits, spilling and output buffer backpressure are left out.
    •
