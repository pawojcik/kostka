kostka architecture notes

kostka, Spark and Trino

kostka's compiler has the same shape as Spark's Catalyst. Its coordinator hands splits to workers as they ask, as Trino's does, and recovers lost work from lineage, as Spark does. The differences come from what the big engines need and kostka doesn't: running across many real machines, and running fast.

How work is distributed

Spark cuts a query into stages and runs each stage as a batch of independent tasks. Trino starts every stage at once and streams pages through long-lived drivers. kostka simulates a coordinator and workers; its unit of work is a split, handed out as workers report the last ones done, and a pipeline starts once the buffers it reads are complete.

Spark: job → stage → task

An action (collect, write, count) becomes a job. The driver's DAG scheduler cuts the physical plan wherever a shuffle is needed, and each stage runs one task per partition. A task holds one executor core, a slot, from start to finish.

Where Spark's tasks come from

Scan stages: one task per input split, about 128 MB by default (maxPartitionBytes). After a shuffle: one task per shuffle partition, 200 by default (spark.sql.shuffle.partitions); AQE merges small partitions and splits skewed ones once it sees the map output sizes. Inside a stage: whole-stage codegen fuses scan → filter → project → partial aggregate into one loop, so the task is the only unit.

How Spark's stages run

A stage is submitted when all its parents have finished, because map tasks write shuffle files and reduce tasks fetch them: every shuffle is a barrier. Stages that don't depend on each other, like stages 1 and 2, are submitted together and share the free slots. A freed core takes the next pending task, preferring local data, so many small tasks balance the load. A broadcast join avoids the shuffle: the driver collects the small side and sends it to every executor.

Trino: stage → task → pipeline → driver → operator

A stage is one plan fragment, and each stage has a task on every worker that runs it. Inside a task the fragment is cut into pipelines at local breakpoints such as a join build. A pipeline runs as one or more drivers, and a driver is a chain of operators that pages pass through.

Where Trino's units come from

Splits: the connector lists splits (a file, row group or byte range), and the coordinator hands them to source tasks in batches as they ask, so a slow worker takes fewer. Tasks: long-lived, one per worker for a source stage, one per hash partition for intermediate stages. Drivers: one per split in a source pipeline, task.concurrency in others. A local exchange can repartition between pipelines of one task.

How Trino's stages run

Each worker has a fixed thread pool shared by the drivers of every task and query. A driver runs for about a 1 s quantum and goes back in a multilevel feedback queue that favours drivers with less CPU used. A driver blocked on a hash build, an empty input or a full output buffer gives its thread up at once. Stages are scheduled up front and pages stream through in-memory buffers, so stage 1 merges while stage 2 still scans. execution-policy can delay probe-side stages until builds are ready. Fault-tolerant mode (retry-policy=TASK) spools exchanges to storage, which makes stages behave like Spark's.

kostka sits between the two. Its splits are pulled as in Trino, but its buffers are complete before they are read and stay where they were written, as Spark's shuffle files do, which is what lets the coordinator make a lost output again by running only the split that wrote it. To move toward Trino, a pipeline would read a buffer while its producer still runs, giving up that simple recovery. Work finer than whole files, such as row groups, would keep one small file from holding back three workers.

What's similar, and why

These are the ideas every engine of this kind arrives at, because they fall out of the problem rather than the scale.

Columns are identified by id

Once rules move nodes around, positions and names stop being reliable, so every column needs a stable identity. kostka arrived at what Catalyst does, even down to printing total#9. Trino gets the same effect from unique Symbols.

Small rules, run to a fixpoint

Each rule rewrites the plan and reports whether it changed anything, exactly like Spark's RuleExecutor, iteration cap included. Why: small rewrites are easy to test, and running them repeatedly lets one rule's output enable another.

The same three rewrites

Predicate pushdown, column pruning and Limit + Sort → top-N exist in all three: TakeOrderedAndProject in Spark, MergeLimitWithSort → TopN in Trino. Why: they are the cheapest large wins: read less, compute less, sort less.

Pipelines cut at breakers

Trino matches most closely. Its HashBuilder runs in its own pipeline, and LookupJoin waits for it through a shared lookup-source object, which is kostka's build buffer, read whole by HashProbe, which builds the table once per worker (or partition) and caches it. In Spark the equivalent cut is the stage boundary, and whole-stage codegen fuses the operators between breakers.

Push inside a pipeline

Spark's codegen uses a produce/consume model: the leaf generates the loop and pushes rows into its parent. Trino operators have addInput / getOutput / finish, and its needsInput() returning false plays the role of kostka's push() returning false, as a Limit's does once it has its rows.

An external trigger

Nothing in kostka runs until it is stepped: one step is one event, such as a split processed or a message delivered. That is a coarse Driver.process(). Trino needs the hook so a small thread pool can time-slice thousands of drivers; kostka needs it so the workbench can stop between any two steps.

Limit stops its input early

Trino's LimitOperator finishes and the driver stops pulling from upstream. Spark has CollectLimit and per-partition limits. All three stop reading files once the limit is reached.

Snapshots and time travel

kostka's snapshot history works like Iceberg or Delta Lake tables, which Spark and Trino read with VERSION AS OF. In all of them, a query pins one snapshot and never takes locks.

What's different, and why

Most of these are things that only pay off with many machines, large data or a JIT compiler underneath.

Distribution

kostka
a simulated coordinator and workers; splits and shuffle, broadcast and gather buffers
Spark
shuffles between stages; tasks per partition
Trino
exchanges between fragments; splits assigned to workers

Why: splitting a plan across machines needs exchange nodes, partitioning and partial/final aggregation. kostka has them, but its workers are simulated in one thread: each split runs whole and is placed on its worker's timeline at simulated time, so the timeline shows the workers as if they ran in parallel. See How work is distributed.

Fault tolerance vs latency

kostka
outputs stay on the workers; a lost worker's are made again from lineage
Spark
shuffle on disk; recompute from lineage
Trino
stream in memory; optional spooling

Why: Spark targets long batch jobs, where losing a node mid-job is expected. Trino targets interactive queries, where writing to disk costs too much latency. kostka does what Spark does, so that recovery can be watched step by step.

Physical planning and cost

kostka
per-file statistics; cardinality estimates drive join order and broadcast vs shuffle; runtime filters
Spark
size-based join choice; adaptive re-planning at run time
Trino
cost-based join order and distribution; dynamic filters

Why: choosing well requires statistics. kostka's come only from the catalog's per-file min/max, null counts, row counts and distinct-count sketches, with no runtime re-planning, so its estimates are much rougher than Trino's or Spark's.

Where pipelines end

kostka
Aggregate, Sort and TopN end a pipeline with a buffer
Trino
Aggregation and TopN are ordinary operators inside one pipeline

Why: Trino's driver pulls output from operators, so an operator can start emitting after finish(). kostka's distributed aggregate and sort need their inputs brought together anyway, so it ends the pipeline at a buffer: a unit the coordinator can schedule, and make again if it is lost. That's simpler, but it adds a hand-off.

Expression evaluation

kostka
compiles each expression into JavaScript closures once, called per row
Spark
Java source per stage
Trino
bytecode over whole columns

Why: a closure per node still costs a call per node per row, though the JavaScript JIT inlines some of them. Generating code for a whole pipeline, as Spark does, removes the calls.

Data layout

kostka
batches of row arrays
Spark
binary rows, columnar at the scan
Trino
columnar Pages

Why: columns are cheap to drop or reorder, map directly onto ORC and Parquet, and keep the CPU cache efficient. Arrays of values are the simplest unit to read in a debugger.

Memory and spilling

kostka
a memory limit per worker; output pieces spill to a bounded disk; a hash table or aggregate that doesn't fit fails the query
Spark
spills sorts, aggregations and shuffles
Trino
per-query memory limits, optional spill

Why: on a shared cluster, one query must not take a worker down. kostka's limits are small on purpose, so that spills and out-of-memory failures happen on example data.

Optimizer structure

kostka
each whole rule over the whole tree, one rule after another
Spark
ordered batches + physical strategies
Trino
memo, pattern match per node

Why: Trino's design doesn't need a fixed rule order for correctness, and it scales to hundreds of rules. It is harder to follow, which matters more for kostka than scale does.

Types and errors

kostka
types checked by the analyzer; overflow and casts checked at run time; errors may differ between plans
Spark
static types, optional ANSI mode
Trino
static SQL types, TRY()

Why: all three reorder evaluation, so an error the original order would hit can vanish. ANSI mode and TRY exist partly because of that.

In one sentence

kostka's compiler is a small Catalyst, and its executor hands out splits like Trino and recovers like Spark. Real distribution, adaptive re-planning, code generation and columnar data are left out because they only pay off at scale; workers, buffers, spills and failures are simulated so their effect can still be seen.

In kostka, these stages live in src/sql/ (parser, analyzer, logical plan), src/sql/optimizer/, src/physical/ (planner, pipelines, operators) and src/execution/ (the coordinator, the workers and the simulation); SPEC.md describes the design. Spark and Trino component names are from their public source and docs as of 2026. They describe typical plans, and the exact output of a real cluster depends on version and configuration.
